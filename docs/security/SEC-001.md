# SEC-001 — Privacy for the personal pilot

**Scope:** the owner and a few people they know, following the owner's request
to simplify the earlier research policy. This replaces the formal research
protocol for that pilot. No application or runtime safeguards exist yet; this
document does not itself collect audio or select local/remote processing.

The owner handles questions and problems through existing private communication.
No separate security/data appointments, recruitment process, consent forms or
reporting platform are required. Use the short [pilot note](PILOT-NOTE.md) before
trying the app. ASR feasibility planning can proceed under this simpler scope.

## Practical safeguards

- Start the microphone only after a deliberate action, show when it is active,
  and release it on stop, cancellation or exit. Do not score reference prompt
  playback as the user's recitation.
- Explain briefly whether audio stays on the device or goes to a named service
  before use. Do not silently switch from local to remote processing.
- Keep no persistent recordings or transcripts by default. Bound temporary
  buffers and clear them when processing ends or is cancelled.
- Before sending audio to a service, check its actual retention and training
  settings/terms, explain them accurately, and use a suitable configuration.
  Unknown retention is not zero retention; resolve it before sending audio.
  Use encrypted transport and keep service API secrets out of browser code.
- Keep audio, transcripts, tokens and identifying payloads out of logs, public
  issues, git and CI artifacts. Restrict access to any saved debugging samples.
- Save a sample only with that person's explicit agreement to its concrete
  purpose, who can access it and its deletion date. A private message suffices;
  no additional form is needed. Delete it and its derived/exported/provider
  copies on request or by that date. Check that selected storage/services can
  honor this before saving; do not claim deletion is done until verified.
- Use saved samples only for the agreed debugging purpose. Building a persistent
  research dataset, training a model or sharing samples publicly needs a separate
  decision; permission to simplify this policy does not authorize those uses.

## Small risk and verification checklist

Use these checks when the corresponding code or service is introduced. They are
planned evidence, not tests already passed. Documentation CI cannot prove
microphone cleanup, provider policy or deletion.

| Risk | Practical check | Existing requirements |
| --- | --- | --- |
| Accidental capture, stale uploads or prompt audio being graded | Exercise start/stop, permission denial, device loss, exit, cancellation and late responses; verify capture/queues stop and prompt isolation works. | FR-002, FR-003, FR-008, NFR-R01 |
| Unexpected storage or transmission | Inspect network, browser/server storage, logs and provider settings on success and failure; confirm the pilot note matches. | NFR-P01, NFR-S01 |
| Saved samples outlive the agreement | Track agreed samples and their copies privately; check deletion on request/date, including derived data and backups. If a service cannot meet the agreement, do not save there. | NFR-P02 |
| Exposed keys, malicious inputs or unsafe dependencies/models | Keep keys server-side where applicable; validate input size/type, escape untrusted output, and review dependencies/model loading and permissions. | NFR-S01 |
| Wrong Qur’an text, prompt timing or overconfident feedback | Verify sources, rights, checksums and mappings; retain qualified content review for content changes, preserve display text, and show uncertainty without false blame. | FR-006, FR-010, NFR-I01, NFR-I02, NFR-A04 |

## Questions, incidents and later scope

Friends can tell the owner privately if something goes wrong. The owner should
stop the affected feature, restrict or remove exposed data, revoke exposed keys,
fix the cause and tell affected people what happened. Do not publish sensitive
details while seeking help. No invented security address or response SLA applies.

GitHub private vulnerability reporting is optional for this pilot. Earlier
inspection found it disabled, and an enablement attempt returned HTTP 403.
The owner may enable it in [security settings](https://github.com/thakurshadman/quran-hifz/settings/security_analysis)
if useful; it is not a blocker for owner-and-friends use. Establish an appropriate
private reporting route and support responsibilities before a public release.

Revisit the policy before unfamiliar people join, public release, a persistent
dataset or model training. Structured research needs purpose-specific consent,
access, retention, withdrawal and rights arrangements before recruitment or data
collection. A representative ASR benchmark is separate from a small personal
pilot; pilot results must not be presented as representative accuracy evidence.

## Completion and boundaries

SEC-001's pilot documentation is complete when this scope, practical safeguards
and short notice are reviewed. Applicable runtime checks belong to implementation
tickets before the relevant feature is used; they are not claimed complete here.
Architecture and ASR targets remain undecided/unchanged. Required code review, CI,
branch protections and qualified Qur’an-content review are unchanged. This policy
change still follows human review; it does not expand automatic merge authority.
