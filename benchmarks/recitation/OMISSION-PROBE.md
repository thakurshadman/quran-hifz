# Can a missing sound produce useful feedback?

This is the first development check for [ASR-004 #7](https://github.com/thakurshadman/quran-hifz/issues/7).
It asks whether a missing sound can be flagged while the same word in an
intended-correct recording remains unflagged. It is not a recitation grader.

## Freeze the rule, then run

The [protocol](omission-protocol.json) fixes the reference version, recitation
settings, sound alphabet and decision rule before this run. These are development
recordings already discussed during model research, not a blind or held-out test.
No claim of independent validation is made by freezing a rule at this stage.

1. Give Muaalem only the full audio, using the [raw sound adapter](MUAALEM.md).
2. Separately obtain a reference from the pinned official phonemizer. Select a
   target word with one word of context on each side in the same ayah.
3. Match that window against the sound output using minimum edit distance.
   Keep complete QPS sound groups, including vowels and length marks.
4. Require one optimal alignment, at least one matched group on each side and
   at most two context edits. Otherwise return **unsure**.
5. For the target, a deletion-only difference with some matching sounds returns
   **possible omission**. Substitution, insertion or total loss returns **unsure**.
   An exact target returns **no target difference**, not “correct recitation.”

Multiple equally good alignments, including repeated matching windows, return
unsure. This first probe does not diagnose repeats. A separate repeat detector
and broad tajweed judgments are outside this stage.

A minimum edit path is a text comparison, not calibrated acoustic confidence.
The context budget is a provisional development setting, not a proven threshold.
Passing requires both the known omission to be flagged and the control target
not to differ. **An unsure control does not pass.** Do not tune the settings on
these recordings and then call the same recordings an independent test.

## Reference integrity

[Quran Transcript](https://github.com/obadx/quran-transcript/tree/a0417aa3ec6154cfebf00bf3806c76dc59655221)
0.6.4 provides a deterministic phonemizer and source-to-sound mappings.
The protocol records every installed package Python/JSON file hash and all
Moshaf attributes. Hashes are checked before importing it. Software is MIT;
its bundled Tanzil Uthmani v1.1 text is **CC-BY-3.0 with additional verbatim
preservation and notice conditions**, not MIT. See [Tanzil terms](https://tanzil.net/docs/Text_License).
Keep source text and its notice intact. No Quran text or derived phonetic verse
is copied into this repository; expected words are never generated by an LLM.

The phonemizer processes a full ayah with Hafs settings and an end-of-ayah stop.
The probe selects an internal word window through its character mappings,
avoiding ayah-boundary pause differences. Madd settings are fixed in the protocol.
Unsupported sound symbols and incomplete tokenization return unsure.
Version/hash checks do not replace a qualified review of the reference or the
recordings. Such content review remains missing; findings are provisional.

## Repeat locally

Use Python 3.12.14, Linux and FFmpeg. Keep audio and outputs outside Git.
The separate runtime uses Torch 2.8.0 CPU and Transformers 4.57.6, adding the
pinned reference package and its locked dependencies. It adds disk space and
maintenance but no paid service or production dependency. This avoids manually
inventing pronunciation references. The lock is version-pinned, not a complete
package security audit; review version changes before rerunning. The reference
package depends on Levenshtein (GPL-2.0-or-later), alongside MIT/BSD-style
packages. These are isolated local research tools; distributing an application
with them would need a separate license assessment.

```sh
python3.12 -m venv /var/tmp/omission-env
/var/tmp/omission-env/bin/pip install --index-url https://download.pytorch.org/whl/cpu 'torch==2.8.0+cpu'
/var/tmp/omission-env/bin/pip install -r benchmarks/recitation/omission-requirements-linux-cpu.lock
/var/tmp/omission-env/bin/pip check
/var/tmp/omission-env/bin/python benchmarks/recitation/muaalem.py download --cache /var/tmp/muaalem-model
mkdir -p /var/tmp/omission-tmp
TMPDIR=/var/tmp/omission-tmp /var/tmp/omission-env/bin/python benchmarks/recitation/muaalem.py run \
  --cache /var/tmp/muaalem-model \
  --runtime-lock benchmarks/recitation/omission-requirements-linux-cpu.lock \
  --audio /path/to/authorized-control.wav \
  --audio /path/to/authorized-omission.wav \
  --output /var/tmp/private-sounds.json
/var/tmp/omission-env/bin/python benchmarks/recitation/omission_probe.py \
  --input /var/tmp/private-sounds.json --output /var/tmp/private-diagnostic.json \
  --sura 1 --aya 7 --word 3
```

The location is a reproducible example of an internal-word probe. Targets need a
word on each side. Inference never receives this location or its reference.
The optional Muaalem runtime-lock argument records the declared environment's
hash; it does not install or independently verify the environment.

Both JSON files are private. Delete them after the agreed analysis, including
partial leftovers after interruption. Diagnostics omit transcript text but are
still personal results. Originals remain untouched. Do not upload either file.
All generic code, protocol and synthetic tests are public; private case results
are not a public accuracy benchmark.

## Later held-out test

Only after the control/omission development check is useful, select a separate,
licensed set from several speakers with human-verified spoken-sound labels.
Freeze its selection and settings before running. Count missed omissions, false
alarms and unsure results separately; never remove unsure cases to improve a score.
If the first check is inconclusive, report that and keep this stage open rather
than claiming the larger test passed. No new-speaker evaluation has run here.
